# line-lock 설계 로그

> 진행하면서 결정된 사항을 계속 누적 기록. 프로젝트 끝나면 이 로그를 바탕으로 README/설계 문서 정리 예정.

## 프로젝트 핵심 개념

- 공장에 여러 대의 설비가 있고, 각 설비에 작업을 배정(예약)한다.
- 핵심 문제: 여러 작업지시가 **동시에 같은 설비**를 예약하려 할 때 발생하는 race condition을 안전하게 처리하는 것.
- 학습 로드맵: 락 없음(버그 재현) → 비관적 락 → 낙관적 락 → Redis 분산락 → 부하테스트 비교
- 확장: 아두이노 센서(버튼)로 설비의 실제 가동 상태를 감지해서 백엔드에 반영 (ESP-01 와이파이 모듈, 3.3V 레벨 시프팅 필요)

## 설계 결정 사항

- **작업지시 : 설비 = 1 : 1로 스코프 확정.** (하나의 작업지시가 여러 설비를 동시에 요구하는 케이스는 데드락 문제로 이어져 이번 스코프에서 제외. 확장 아이디어로 문서에 명시 예정)
- **설비 : 작업지시 = 1 : N.** 설비 하나는 시간에 따라 여러 작업지시를 거쳐감 (표준적인 예약 시스템 패턴, 콘서트 좌석/호텔 객실 예약과 동일 구조)
- 레포는 개인 계정에 생성 (조직 계정 아님), 이름 `line-lock`

## 엔티티 설계

### Equipment (설비) — 확정

| 필드 | 타입 | 설명 |
|---|---|---|
| id | Long (PK) | JPA 자동 생성, 내부 식별자 |
| equipmentNumber | String (unique) | 사람이 쓰는 고유 설비번호 (예: EQ-001) |
| status | Enum (RUNNING, IDLE, MAINTENANCE) | 가동중/대기/점검. 아두이노 센서가 이 값을 갱신하게 될 예정 |
| version | Long (`@Version`) | 낙관적 락용 필드 |

**낙관적 락 개념 정리 (학습 노트):**
- 비관적 락: 충돌을 미리 가정하고 DB 행을 잠가서 다른 요청을 대기시킴 (`SELECT ... FOR UPDATE`)
- 낙관적 락: 잠그지 않고 진행하다가, UPDATE 시점에 `WHERE id=? AND version=?` 조건으로 충돌 여부를 검사. 조건에 안 맞으면(영향받은 행 0건) `OptimisticLockException` 발생 → 재시도 로직으로 처리
- 두 락 모두 "실제 발생하는 상황"이 아니라, 같은 문제(설비 동시 예약 충돌)를 해결하는 서로 다른 구현 방식이며, 4단계 로드맵에서 각각 직접 구현하며 비교할 예정

### WorkOrder (작업지시) — 확정

작업지시와 예약을 하나의 엔티티로 통합 (1:1이라 분리 불필요 — 불필요한 엔티티 쪼개기 방지, YAGNI)

| 필드 | 타입 | 설명 |
|---|---|---|
| id | Long (PK) | |
| equipment | Equipment (`@ManyToOne`) | 예약 대상 설비 |
| requester | User (`@ManyToOne`) | 요청자 |
| description | String | 작업 내용 |
| startTime | LocalDateTime | 사용 시작 시간 |
| endTime | LocalDateTime | 사용 종료 시간 |
| status | Enum (PENDING, CONFIRMED, FAILED, COMPLETED) | 작업지시 상태 |

**상태값 설계 노트**: "취소(사용자 자발적)"과 "실패(락 경쟁에서 밀림, 비자발적)"는 의미가 달라서 원래는 분리하려 했으나, 이번 스코프에서는 자발적 취소 기능 자체를 빼고 `FAILED`(락 경쟁 실패)만 남기기로 결정. 부하테스트 결과에서 "락 경쟁 실패 횟수"를 명확히 집계하기 위한 선택. 자발적 취소 기능은 향후 확장 아이디어로 남김.

**멀티 설비 작업지시 관련 노트**: 하나의 작업지시가 여러 설비를 동시에 요구하는 케이스는 데드락(락 획득 순서에 따라 서로 기다리는 문제) 이슈로 이어져서 이번 스코프에서 제외. 표준적인 동시성 학습 프로젝트(콘서트 좌석 예약, 쿠폰 발급 등)도 대부분 1:1 구조를 사용.

### User (사용자) — 확정

| 필드 | 타입 | 설명 |
|---|---|---|
| id | Long (PK) | |
| loginId | String (unique) | 로그인 아이디 |
| password | String | BCrypt 암호화 저장 |
| name | String | 이름 |
| role | Enum (ADMIN, USER) | 권한 구분 |

## ERD 요약

```
User (1) ──< WorkOrder >── (1) Equipment
              (요청자)         (예약 대상)
```

- User 1 : N WorkOrder
- Equipment 1 : N WorkOrder
- WorkOrder : Equipment = 매 순간 1:1 (동시 다중 설비 요구 제외)
